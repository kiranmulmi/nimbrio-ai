# Agent core (`@app/agent`)

The agent itself, with no HTTP and no database. `src/index.ts` is the public API used by `@app/db`, `@app/api` and `@app/cli`.

- `agent.ts`: the loop. Plan (planning step decides direct vs plan), act (model + tools), check (open plan steps go back once), limit (a tool-free summary when out of steps or tokens).
- `planner.ts`: the planning decision and plan state. `prompt.ts`: every prompt the model sees.
- `llm.ts`: the only file that calls the model (OpenAI Chat Completions, streamed), except Cursor's models, which it hands to `cursor/caller.ts` (`ModelSettings.provider === 'cursor'`). `createModelCaller(settings: ModelSettings)` returns a `CallModel` either way. The model is not in `AgentConfig`: apps pass it per run as `createAgent({ model })` (from `@app/db`'s `store.models`). Tests pass a fake `callModel`. Token counts come from `readUsage`: `inputTokens` is always the whole input, with `cachedInputTokens` (read from the server's prompt cache) and `cacheWriteTokens` beside it, from either OpenAI's `prompt_tokens_details.cached_tokens` or Anthropic-style `cache_read_input_tokens` / `cache_creation_input_tokens` (some proxies leave writes out of `prompt_tokens`; it adds them back). The servers cache on their own; keep the prompt prefix stable (no timestamps, fixed tool order, append-only conversation) so they can.
- `guardrails.ts`: input checks, step/token budget, the file sandbox (`resolveInWorkspace`, `assertCanChange`, `prepareWorkspaceFolder`, `APP_DATA_FOLDER`), the command backstop (`refuseCommand`, `commandEnv`), the private-address block (`assertPublicUrl`), CLI approvals.
- `config.ts`: `loadAgentConfig(env)`. The only place env is read, and only when an app calls it: just `AGENT_LOG_DIR`, with the default `AgentSettings`. The behaviour settings (planning, limits, approvals, SearXNG, log level) are set in the app; apps merge the saved ones (`store.settings`) over this per run.
- **Token usage**: every model call goes through `callRecorded` in `agent.ts`, which times it and records it on the run's `Budget` (`RunResult.calls`: kind, model, duration, tools asked for, tokens) with what its tokens went to (`usage-breakdown.ts`: `inputBreakdown` by system prompt section (`systemPromptSections` in `prompt.ts`), tool definition, the user's words vs context the app added, notes, summary, earlier turns, each tool result and images; `outputBreakdown` by reply text, tool calls and the rest as reasoning). The server reports totals only, so parts are counted like the context meter and scaled to them.
- `title.ts`: `suggestChatTitle(callModel, userMessages)`, a short tool-free call that names a chat, and `cleanTitle` for its reply.
- `improve.ts` / `write-instructions.ts` / `improve-skill.ts`: one tool-free call each, for the composer's improve button, the workspace form's instructions assistant and the skill form's Improve (`improveSkill`: instructions plus a suggested description, as JSON) (`writeInstructions`; the project summary it gets is marked as data).
- `memory/`: `short-term.ts` (the conversation, append-only so servers can cache prefixes), `long-term.ts` (`MemoryStore` interface, the JSON `LongTermMemory` the app uses as `.nimbrio-ai/memory.json`, keyword ranking). `file-io.ts`: atomic writes and per-file queues.
- `mcp/`: MCP servers as tools. `hub.ts` (`McpHub`) starts and reuses each workspace's servers (stdio, Streamable HTTP with SSE fallback), restarts them on config change and stops idle ones; `tools.ts` turns their tools into `AnyTool`s (`mcp__<server>__<tool>`, approval unless auto-approved). Passed to the loop as `createAgent({ extraTools })`. They are deferred (`buildToolset`: `deferred`, `deferredSummary`, `definitionsFor(loaded)`): the system prompt lists them by name and first sentence, and only the ones the model loads with `load_mcp_tools` (exact names, or a prefix ending in `*`) are sent as definitions, for the rest of the run. MCP tools the chat already called are loaded at run start, so its history matches the tools sent. MCP schemas are large (Atlassian's 26 tools are ~70K characters), so don't send them eagerly.
- `cursor/`: Cursor's private API, ported from OmniRoute's reverse-engineered codec (field numbers in the comments). `auth.ts`: the browser sign-in (PKCE `loginDeepControl` + `auth/poll`), token claims and renewal (`exchange_user_api_key`). `client.ts`: requests present as the Cursor CLI (`CLIENT_VERSION`, `cursorHeaders`); `fetchCursorModels` (AvailableModels as JSON) and `cursorAgentUrl` (GetServerConfig field 27, only `*.api5.cursor.sh`, cached an hour). `wire.ts`: protobuf varints/fields, `google.protobuf.Value`, Connect framing. `protocol.ts`: the `agent.v1.AgentService/Run` messages. `caller.ts`: one HTTP/2 Run stream per model call: the system prompt and the whole conversation as one labelled user text (`conversationText`, Cursor's agent takes one user message); images view_image opened go with it as `UserMessage.selected_context.selected_images` (`SelectedImage` data/uuid/mime_type, as the Cursor CLI's ACP mode sends them; `conversationImages`), numbered in the text where the images message was; our tools are declared as the `nimbrio` MCP server (in the run request, the request-context answer and the mcp_state answer, which Cursor waits for). It answers the server's key-value and exec requests on the same stream, declines Cursor's own tools (read, shell, ...: typed rejections, the generic exec throw for the rest) so only our approved tools run, and ends the turn at `turn_ended`, the end of the stream, or 400 ms after the first MCP tool call (parallel calls), returning them as ordinary tool calls whose results go back in the next call's text. Composer models put their reply in the thinking text after `</think>` (`composerReply`); other models' thinking isn't shown. Reasoning effort is sent as the `reasoning` (GPT) or `effort` setting. Cursor's input token count already includes the cache (`toUsage`). Offline tests: `test/cursor.test.ts`; the live stream was checked by hand against composer, Claude and GPT models.
- `attachments.ts`: the `AttachmentStore` interface for files the user attached (kept by `@app/db` in `.nimbrio-ai/uploads/`), passed as `createAgent({ attachments })`; `agent.run(prompt, { attachments })` lists them after the message. `tools/attachments.ts`: `read_attachment` (PDF via `unpdf`, `.docx` via `mammoth`, text), `view_image` (queues the image; the loop adds it as an internal user message with `images: [id]` after the tool results, and `llm.ts` sends it as an `image_url` part) and `save_attachment` (needs approval).
- `skills.ts`: the `SkillStore` interface for the workspace's skills (kept by `@app/db` in `.nimbrio-ai/skills/<name>.md`), passed as `createAgent({ skills })`. Each run lists them in the system prompt and the planner input (`renderSkills`: name and description, read at run start); `use_skill` (`tools/skills.ts`, read-only) loads one in full. `agent.run(prompt, { skills })` adds the skills the user picked after the message (`pickedSkillsContext`) and saves their names on it (`skills` on the user message).
- **Tool groups**: `buildToolset(extra, disabledGroups)`. A workspace can turn off `files`, `commands`, `web`, `memory`, `plans` (`TOOL_GROUPS` in `@app/shared`, `GROUP_OF` in `tools/index.ts`): their definitions aren't sent, `basePrompt(off)` in `prompt.ts` leaves out their guidance (with every group on it is the full `SYSTEM_PROMPT`, word for word), and a call to one refuses. Attachment tools are sent only when the chat has files, `use_skill` only when there are skills, MCP tools only once loaded; tools the chat already called are always sent so its history stays valid. `createAgent({ disabledTools })`; `runInChat` passes the workspace's, and its planning choice (`planning: default | auto | off`; plans off means planning off).
- **Steering** (messages the user sends mid-run): `createAgent({ steering })`, a `SteeringInbox` (`take()` hands out the waiting `SteeringMessage`s once each). The loop takes them before each model call (so after a step's tool results, never between a tool call and its result) and once more when the model gives a final answer, which then continues instead of finishing. Each becomes a user message (`steeringMessage` in `prompt.ts` around the text, `display` the text, `steeredAt` the time it was sent, saved in the chat), is appended to the run's `request` (planner, summaries, write-up at the limit), and is reported as a `steer` event. Without `steering` a run reads none (the CLI).
- **Voice replies**: `createAgent({ voiceReplies })` (from the workspace's `voiceMode`, via `runInChat`) adds `VOICE_REPLIES` to the system prompt, before the workspace instructions: short spoken sentences, no Markdown, code or URLs read out.
- `tools/`: one file per tool plus the `index.ts` registry; `tools/files/` holds the file tools and `walk.ts` (tree walk, skipped folders, globs); `run-command.ts` runs bash in the workspace (own process group, timeout, leftovers stopped; `tools/shell.ts` holds the shell choice, group signals and the bounded output both it and background tasks use). Live events use `AgentEvent` from `@app/shared`.
- **Context window** (`context.ts`): every model call is kept inside the model's window (`ModelSettings.contextWindow`, or `createAgent({ contextWindow })` in tests, else `DEFAULT_CONTEXT_WINDOW` 128K from `@app/shared`), minus room for the reply (`maxTokens`, at most half; else a tenth). `prepareRequest` in `agent.ts` estimates each request (characters / 4 for system prompt, tool definitions, messages; ~1,500 per image), corrected by the server's reported input tokens (`ContextMeter.calibrate`). At 80% (`COMPACT_AT`) `compact` summarizes the older part of the model's view in one tool-free call per chunk (`COMPACTION_PROMPT`, `transcriptChunks`), keeping the newest ~25% word for word (`compactionCut`, never starting on a tool result); the summary (`summaryMessage`: summary, current plan, saved memories, and this run's request word for word if it was covered) is appended as an internal user message with `summaryOf` (`Conversation.addSummary`), and `Conversation.forModel()` sends it in place of the messages before `summaryOf`. Nothing is deleted, so the chat (and its saved rows) keep everything; the summary rewrites the prompt's start once, so server caching restarts there. Past 95% (`HARD_LIMIT`) the oldest tool results (not the latest batch) are replaced by a stub for that call only (`shrinkToolResults`). Tool output and the memory list are capped relative to the window (`contextLimits`); only images still in the model's view are loaded. Events: `context` after each call (used tokens of the window), `compaction` when it summarizes.
- **Background tasks**: `background-tasks.ts`. `run_command` with `background: true` starts the command as a task (no timeout; it still needs approval) and returns its first 4 s of output; `task_output` (read-only) lists the workspace's tasks or reads one's state and output, `stop_task` (needs approval) ends one and everything it started. The app holds one `BackgroundTasks` for its life and each run gets `forWorkspace(path, chatId)` as `createAgent({ tasks })` (`ToolContext.tasks`), so a chat only sees its own workspace's tasks. At most 10 run per workspace; the last 10 stopped ones are kept for reading. A task whose shell exits has its leftovers stopped; `close()` / `closeWorkspace()` stop them on shutdown or when a workspace is deleted or moved. Without `tasks` (e.g. a test) background starts refuse.

## Adding a tool

1. Create `src/tools/my-tool.ts` with `defineTool({ name, description, properties, run })`. The description says _when_ to call it: that text is how the model decides.
2. Register it in `src/tools/index.ts`.
3. Set `needsApproval: true` if it changes anything outside the agent (writes files, sends messages, spends money). Such tools (and MCP tools that ask first) automatically get an optional `reason` argument, one sentence for the user that the approval card and CLI prompt show as "Why"; `runValidated` strips it, so `run` never sees it. Arguments the model may leave out go in `optional` (null counts as left out).
4. Add an offline test in `test/` and an eval case in `evals/cases.json`.

`npm run test -w @app/agent` is free (fake model). `npm run eval -w @app/agent` calls the real model named by `EVAL_MODEL` / `EVAL_BASE_URL` / `EVAL_API_KEY` in the root `.env` and costs money.
