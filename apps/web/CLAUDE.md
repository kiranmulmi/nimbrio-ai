# Web app (`@app/web`)

React 18 + Vite + Tailwind 3 + react-router 7. Full rules: `docs/standards.md` (Frontend).

- **Data**: every call goes through `src/lib/api.ts` (`VITE_API_URL`, default same origin). Types and Zod schemas come from `@app/shared`; never redeclare them. Server state never goes in `localStorage` (UI prefs only: theme, panel width/tab).
- **Answers**: agent text renders through `components/Markdown.tsx` (`react-markdown` + `remark-gfm`: CommonMark and GitHub tables, task lists, strikethrough, autolinks). It builds React elements, shows any HTML in the text as plain text, opens links in a new tab, shows images as links, and colours JSON code blocks (`CodeText`). `components/CopyButton` copies a message: under a user bubble (on hover/focus, always on touch screens), and at the start of a finished reply's steps line (its answer text as Markdown, without interim notes or errors).
- **Plans**: shown in the conversation, not the side panel. A `create_plan` call leaves a `plan` flow item (`conversation.ts`); `planPlacement.ts` matches each to the chat's plans (`earlier` then current), and `AgentMessage` draws a `PlanCard` there. Steps show inline: an `update_plan` that starts a step (or finishes one never started) leaves a `step` flow item, and `flowSections.ts` groups the tool calls, interim text and approvals after it under that step's `PlanStepSection` (number, status, text, note) until the next step, plan, note, answer or error. A plan with inline steps gets a short card (goal, progress, Done when); one without (older chats) keeps the foldable full list (`EarlierPlan`). The current plan's live progress is also in `PlanDock` above the composer (shown while it has open steps or the agent works on it). `add_plan_steps` leaves a note. The run's planning step leaves a `thought` flow item at the start of the reply, drawn by `ThoughtLine` as "Thought for 12s" once it decides (timed live from the `planning` to the `route` event; after a reload, the `planner` call's `durationMs` in the `meta` item). Offline tests: `apps/web/test/plan-steps.test.ts`, `apps/web/test/thought.test.ts` (`npm run test -w @app/web`).
- **MCP**: servers are set up in Settings → MCP servers (`features/mcp/McpServersPage`, form at `/settings/mcp/new` and `/settings/mcp/:name/edit`); a workspace turns them on in its settings form (`McpServerSwitches` in `features/workspaces/AgentChoices`, saved after the workspace with `PUT …/mcp/enabled`); the side panel's MCP tab (`McpPanel`, in its lower section) lists only the servers on there, one compact `McpServerRow` each (dot, name, tool count that folds open the tools with Always allow, restart and edit on hover, a switch to turn it off), and reloads when the workspace form saves.
- **Context window**: the model form (`features/models/ModelFormPage`) has an optional Context window field with 32K / 128K / 200K / 1M quick picks (empty: 128K). The chat state keeps the last `context` event (`ConversationState.context`), shown by `ContextMeter` at the end of the composer's token line (a thin bar and "Context 42% of 200K", amber from 80%, where summarizing starts); a `compaction` event, or a `compaction` history item after a reload, adds a note in the chat where older messages were summarized (they still show).
- **Token usage**: the token counts on each reply's steps line and on the composer's token line are buttons (dotted underline, `TOKENS_BUTTON` in `AgentMessage`); both open `features/chat/TokenUsageDialog` (state in `ChatView`). From a reply: each model call (`RunResult.calls` / the history `meta` item's `calls`: kind, model, duration, tools asked for, tokens). From the chat: each message's total (`tokenUsage.ts` `messageUsages`, labelled with the message that started the run), folding open to its calls. Bars split cached input / new input / output in `--usage-*` colours (`bg-usage-*`). Each call also carries what its tokens went to (`input` / `output`: `TokenGroup`s, estimated by `@app/agent`'s `usage-breakdown.ts`); `Composition` shows them as share bars, per request (its row folds open) and added up for the reply or chat (`mergeGroups`, so a result re-sent on each step counts each time). Replies saved before calls were recorded show their total only. Offline tests: `apps/web/test/token-usage.test.ts`.
- **Runs**: `POST /v1/runs` is read with `src/lib/sse.ts`. `features/chat/conversation.ts` is the reducer that turns saved history and `StreamEvent`s into what the chat shows; `useConversation` owns the stream.
- **Steering**: while this tab's run works, the `Composer` stays enabled (`onSteer`): Enter / the teal Send next to Stop posts the text to `POST /v1/chats/:id/run/messages` (`useConversation.steer`; files and picked skills stay in the box). Until the agent reads it, it's listed above the box in `ChatView` (`queued`); its `steer` event removes it there and adds a user turn (`isSteer`, "Sent while the agent worked" under the bubble) followed by a new agent turn, so the run's steps line ends up under the last one (history items with `steer: true` draw the same). Messages still unread when the run ends, or refused, go back into the box (`returned` → `restoreDraft`) with a warning toast. Voice mode doesn't steer (it has Interrupt). Offline tests: `apps/web/test/steering.test.ts`.
- **Routes** (`src/App.tsx`): `/settings/models`, `/settings/models/new`, `/settings/models/:id/edit` (app-wide models), `/settings/agent` (app-wide agent settings; `SettingsTabs` switches between the two), `/workspaces/new`, `/workspaces/:id/settings`, `/settings/mcp`, `/settings/mcp/new`, `/settings/mcp/:name/edit` (form pages using `usePageHeader` + `Topbar`), `/workspaces/:id` and `/workspaces/:id/chats/:chatId` (the chat screen, one parent route so it stays mounted when a new chat gets its id).
- **Side panel**: `features/panel/SidePanel` (the Files tree uses VS Code's UI font, `font-explorer` in `tailwind.config.js`, 13px, compact rows, and fades what git ignores, `WorkspaceFiles.ignored`, a folder's contents too): Files, Terminal, Git diff and Tasks as the top tabs (Terminal and Git diff each only where the workspace's Planning & tools tab turns it on under Side panel tabs, `hasTerminalTab` / `hasGitTab`, both off by default; `visiblePanelTabs` in `panelTabs.ts`, and `ChatScreen` shows Files when the remembered tab is hidden; their icons hide when the strip is under 400px; `tasks/TasksPanel`: a `$` command box on top (Enter or Run starts it in the background in the workspace folder via `POST …/tasks`, toasts, opens its output; errors such as a refused command show under the box), then the background tasks running, the agent's and the user's, from `useRunningTasks`, which `SidePanel` polls every minute while the browser tab is showing (paused while hidden, `lib/usePageVisible`; the git change count and an open task's output pause too) and on each run start/end so the tab shows a running count; each row has a live dot, the command, its folder, elapsed time and Stop (`DELETE …/tasks/:taskId`, toast), and opens its output, fetched every 1.5 s and following the end; only running tasks are listed, so a stopped one drops off; `files/FilesPanel`: a search toolbar, Name or Content, via `GET …/files/search` in `useFileSearch`; a result opens `FilePreview` at the matching line. `FilePreview` edits too: Edit swaps in `CodeEditor` (CodeMirror 6, lazy-loaded with its language modes, coloured with the same `hljs-*` classes), Save / ⌘S sends `PUT …/files/content` with the version it opened, and a 409 offers Reload or Overwrite; unsaved edits ask before closing. New files and folders come from the toolbar or a row's ⋯ menu / right-click (`RowMenu`: New file, New folder, Rename, Delete). Naming is inline in the tree with `NameInput`: a new entry's box is the first row inside its folder (`POST …/files`), a rename replaces the row (`PATCH …/files`) and delete asks in `ConfirmDeleteDialog` (`DELETE …/files?path=`); `git/GitPanel`: changed files since the last commit, each opening its diff in `DiffView` with line numbers and both sides syntax-highlighted; reloads when a run ends); below them `LowerPanel` holds Skills (first, the default), Memory and MCP in their own tabs (`features/skills/SkillsPanel`: the workspace's skills, each opening the `SkillDialog` popup, as does New skill here and in the composer's Skills menu, through `SkillDialogProvider` / `useSkillDialog` around the chat screen, which also updates the list; closing with unsaved changes asks first; its Improve button rewrites the instructions via `POST /v1/prompts/skill` and fills an empty description with its suggestion, with Undo; delete behind `ConfirmDeleteDialog`) (its top edge drags to resize, double-click resets, the chevron folds it to its tabs; tab, height and fold are UI prefs).
- **Tool inputs**: each finished tool call's row shows its tool's own icon (`features/chat/toolIcon.tsx`: a map by tool name, a server for `mcp__*` tools, a wrench for anything else; spinner while running, cross on failure). `features/chat/ToolInput` shows a tool's arguments by kind: `write_file` as highlighted code, `edit_file` as a diff, `run_command` as a shell line, everything else (MCP tools too) as `InputFields`, a labelled list (long text in a box, Markdown rendered when it looks like Markdown, lists as chips, nested data as coloured JSON) with a Raw JSON toggle. Never show the raw argument JSON by default.
- **Voice mode**: a workspace's Chat mode (Voice tab, `ChatModeChoice`) saves `voiceMode`. With Voice picked, the tab shows `features/workspaces/VoiceSettings`: microphone (`useMicrophones`: `enumerateDevices`, Allow access when names are hidden), voice (with Play sample), speed and pitch. They're this browser's UI prefs (`chat/voicePrefs.ts`: `agent.micId`, `agent.voiceName`, `agent.voiceRate`, `agent.voicePitch`), written when the form saves; `useVoicePrefs` keeps open hooks current. `startRecognition`'s `micId` opens that mic with `getUserMedia` and hands its track to `recognition.start(track)` (Chrome 135+), falling back to the default mic. When on, `ChatView` shows `VoiceBar` instead of the `Composer` (a status pill with a call timer and the caption; round call controls on the right: Start voice chat when idle, Send while listening, Interrupt while replying, and a red End call with a hang-up icon always last; the chat's token line, `ChatUsageLine`, shared with the `Composer`, under it) (the composer stays, with a note, where the browser lacks speech recognition or synthesis). One button starts a live conversation: `startRecognition` (in `useSpeechInput`) listens continuously and a 1-second pause (`SEND_AFTER_PAUSE_MS` in `VoiceBar`, restarted by every word heard; the browser's own end-of-speech cut in too soon) sends it as a normal message (8 s with nothing heard ends the conversation); the reply is read aloud as it streams (`useConversation`'s `subscribeReply` gives the raw text deltas and a `break` at each tool call; `speechText.ts`'s `createSpeechSplitter` hands back finished sentences without code or Markdown; `useSpeechOutput` queues them on `speechSynthesis` in the most natural voice for the page language (Natural / Premium / Enhanced, then Google; the workspace settings' Voice tab overrides it, saved as the `agent.voiceName` UI pref; the bar has no voice picker)), then it listens again. The mic is only on while it's the user's turn (listening while the reply plays let the speakers' echo interrupt it, and opening the mic mid-reply made the voice drop out): the coral Interrupt button, shown while it replies, stops speech and the run and listens; what's said is sent once the run has stopped. While it waits on the agent (Thinking: no speech, no approval pending, not stopping) `useThinkingSound` loops the bubble-pop clip `public/sounds/thinking.mp3` with Web Audio (decoded once, gapless `loop`, one shared `AudioContext` suspended while silent; it starts only after a short delay so the gaps between spoken sentences stay quiet, and fades out). The chat keeps pace with the voice: each `SpokenSentence` from the splitter carries where it ends in the reply's raw streamed text (across tool-call breaks, code blocks mapped past), and as it starts being said `VoiceBar`'s `onSpokenUpTo` lets `ChatView` show the newest `AgentMessage`'s text blocks only up to there (`revealUpTo`; tool steps and approvals show at once; null shows all once speech ends, is interrupted, or the bar listens). The sentence being read shows as a caption in the bar; nothing in the chat is marked and words aren't tracked (per-word highlighting ran work on every spoken word and was removed while chasing choppy, robotic-sounding speech). Approvals are announced once and wait for a click (no cut-in listening meanwhile). A text box under it takes a pasted link or note: it's added after the next spoken message (then cleared), or Enter sends it on its own (cutting in like speech).
- **Workspace form tabs**: `WorkspaceFormPage` splits into General (name, folder, delete), Instructions, Planning & tools, Voice and MCP servers tabs (one form, every tab stays mounted so nothing typed is lost; a failed check switches to the tab with the error; arrow keys move between tabs). The tabs are a vertical column beside the form from `md` up (sticky while it scrolls, the same look as the Preferences side tabs), a scrolling row above it on phones. The settings popup is `Modal size="xl"` (up to 1240px wide, a fixed `min(820px, 88vh)` tall so switching tabs doesn't resize it; longer content scrolls inside).
- **Workspace agent choices**: the workspace form's Planning (`Agent settings` / On / Off) and Tools switches (`features/workspaces/AgentChoices`) save `planning` and `disabledTools`; Plans off shows Planning as Off. Its MCP servers section lists the app's servers with a switch each.
- **Instructions assistant**: the workspace form's instructions box is `features/workspaces/InstructionsEditor` (textarea plus an attached AI bar: a request box, Write/Rewrite, one-click chips, Undo); it calls `POST /v1/prompts/instructions` and only fills the box, so the user still reviews and saves.
- **Settings popup**: opened from the chat screen, Models, Agent and MCP servers (and their forms) and the workspace form (`/workspaces/new`, `/workspaces/:id/settings`) show in a popup over the chat (`layout/SettingsModal`): `useSettingsBackground` keeps the chat's location as the background while the URL is one of those pages, and `App` renders the routes at the background plus the same `settingsRoutes` / `workspaceFormRoutes` inside `SettingsModal` (`Topbar inModal`). For the app settings (`/settings/*`) the popup lays them out with `SettingsSideTabs` (`features/settings/SettingsTabs`): Models, MCP servers and Agent settings as vertical tabs on the left (a scrolling row on phones), a sub-form keeping its tab selected; there each page's own horizontal `SettingsTabs` hide (a context), and they stay on full pages. One opened directly or reloaded is a full page. Close goes back to the chat; saving a workspace goes back to the chat it was opened from (`from` state) and `announceWorkspaceSaved` makes the mounted chat screen reload the workspace. A form's buttons go in `FormActions` (`layout/pageHeader`): in the popup's footer bar (Delete / Reset on the left, Cancel and Save on the right), in the top bar on a full page; list pages keep `TopbarActions` at the top, and an empty footer stays hidden. `Modal` closes on Escape only when it's the topmost popup (the folder picker opens over the workspace form).
- **Patterns**: forms on their own pages (skills and the settings popup above are the exceptions, as the user asked); deletes behind `ConfirmDeleteDialog`; a toast after every save, rename and delete (`lib/toast`: `toast(message, kind)` with `success` (default), `error` for failures, `warning` for partial saves or things gone missing, `info`; bottom-right, dismissable, paused on hover, errors stay longest); the URL reflects the open workspace and chat.
- **Look**: every page sits under `layout/AppNav`: brand / workspace switcher as a breadcrumb, then the connection chip (`ConnectionMenu`: approvals, folder, links to Models and Agent settings), theme and workspace settings (`WorkspaceSettingsLink`). On the chat screen at `xl` and up there is no top bar (`AppNav hasSidebar`): `ChatSidebar` carries the brand (`BrandLink`) and the open workspace's name at its top, and Workspace settings and New workspace links (`SidebarLinks`, greyed while the agent works) and the workspace switcher (`WorkspaceSwitcher variant="sidebar" opensUp`, a "Switch workspace" button whose menu opens upward, sorted by recent activity, `lastActiveAt`; only the top-bar variant's menu repeats those two links) at its bottom; the app-wide settings open from the footer's Preferences, which also shows an auto-approve / refuse badge when approvals aren't "ask"; the theme toggle (`ThemeToggle size="sm"`) sits after Preferences at the right end of the footer. Below `xl` the bar stays, since it opens the sidebar drawer. A 32px footer runs along the bottom of the chat screen (a second row of `ChatScreen`'s grid; at `xl` the chat list spans both rows, so the footer starts after it) with a small Preferences link (gear + text, `features/chat/PreferencesLink`) at its right end that opens the app settings popup on Models. Voice input: the composer's mic (`features/chat/useSpeechInput`, the browser's Web Speech API, one utterance: it ends when you pause) puts the words after what's typed, never sends them; hidden where the browser has no speech recognition (Firefox). Chrome turns speech into text on Google's servers. Files are attached in the composer (paperclip, drop or paste; `useDraftAttachments` uploads each one at once to `POST /v1/workspaces/:id/attachments`, the run sends their ids) and shown in the sent message by `UserMessage` / `AttachmentChip`. The model and reasoning effort are picked per message in the composer (`features/chat/ModelControls`, remembered by `useModelChoice` as a UI preference). Skills are picked per message with `SkillPicker` (next to the wand; `ChatScreen`'s `useSkills` feeds it and the Skills tab), shown as `SkillChip`s above the box and on the sent message, and sent as `skills`. Next to them, while approvals are set to ask, `AutoApproveToggle` (remembered as `agent.autoApprove`, shown in warning colours while on) sends `autoApprove` with each message and, flipped during a run, applies it there too (`changeAutoApprove`). Style: teal and navy on a soft mint white (tokens in `index.css`, `--accent` teal, `--ink` navy, `--coral` for warm highlights), Inter (`@fontsource-variable/inter`, set as `--font-sans` in `index.css`), bold headlines with a `.highlight` word, `.tag` pill labels and `.step-number` tiles. Corners follow one scale, `--radius-card` / `--radius-control` / `--radius-small` / `--radius-tiny` in `index.css`, which Tailwind's `rounded-2xl` / `xl` / `lg` / `md` read (avoid one-off `rounded-[…]` values). Cards are rounded `.panel`s with a soft `shadow-card`; `shadow-float` / `shadow-dialog` for menus, drawers and dialogs; `shadow-accent` under teal buttons. Status colour goes through `components/Badge` (pills) or a left border, not filled cards.
- **Install as an app**: a web app manifest (`public/manifest.webmanifest`, linked from `index.html`) with icons in `public/icons/` (`icon.svg` and `icon-maskable.svg` are the sources; the PNGs were rendered from them with headless Chrome at 192/512/180 px). No service worker: Chrome doesn't need one to install, and the app must always talk to the live API. `lib/installApp.ts` keeps Chrome's `beforeinstallprompt` (started in `main.tsx`) so `SidebarLinks` shows Install app while Chrome offers it.
- **Theme**: light/dark/system via `src/lib/theme.tsx` as `data-theme` on `<html>`; colours from the CSS variables in `src/index.css`. `public/theme-init.js` applies it before first paint (a file, not inline, because the API's CSP blocks inline scripts).
- **Dev**: `npm run dev` (root: API and web together) or `npm run dev:web` on :5173 proxies `/v1` to the API on `127.0.0.1:<PORT>` (the root `.env`'s `PORT`, default 4000, read with `loadEnv` in `vite.config.ts`). `npm run build -w @app/web` outputs `dist/`, which the API serves.
