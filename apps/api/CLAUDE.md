# Backend API (`@app/api`)

Express 4 API for the agent: JSON REST under `/v1` plus one streaming endpoint. Full rules: `docs/standards.md`.

- **Layers**: routes stay thin (validate with Zod from `@app/shared`, delegate). Logic lives in `features/<feature>/<feature>.service.ts`. Storage lives in `@app/db` (`Store`), never in this app.
- **Wiring**: `src/index.ts` opens the `Store` (files in `~/.nimbrio-ai/`, no database), moves the old `.agentic-ai` folders first (`store.moveLegacyFolders()`, before the agent logger makes its folder) and starts the server. `src/app.ts` builds the app from an `AppContext` (`store`, `agentConfig`, `agentLogger`, `runs`, `mcp`: the `McpHub` running the workspaces' MCP servers, closed on shutdown). Features are factories (`createXService(context)`, `xRouter(service)`) mounted in `app.ts`.
- **Errors**: throw the typed errors in `src/lib/errors.ts`. `@app/db`'s `InputError` maps to 400. `middleware/error.ts` is the only place that turns errors into HTTP. Don't catch just to log and rethrow.
- **Envelopes**: success `{ data }`, failure `{ error: { code, message } }` (`errorEnvelope` from `@app/shared`). 201 on create, 204 on delete.
- **Runs**: `POST /v1/runs` streams `StreamEvent`s as `data: <json>` SSE frames. `runs.service.ts` validates and claims the chat _before_ the stream starts, so request errors stay JSON. `RunRegistry` tracks one run per chat and pending approvals, and gives each run an `AbortSignal`: `POST /v1/chats/:id/stop` aborts it (from any tab), which cancels the model call, skips unstarted tool calls (they still get a result), stops a running command, denies open approvals, and ends the run as `stopped`. A closed stream (switching chats) does not stop the run. `POST /v1/chats/:id/run/messages` `{ message }` (`steerRequestSchema`, `checkInput`) queues a message for the run in progress (202 `{ id }`; 404 when none runs or it's stopping, 409 past `MAX_WAITING_MESSAGES`); `RunRegistry.inbox(chatId)` is the run's `steering`, and the stream sends a `steer` event with that id when the agent reads it. A run's `autoApprove` (the composer's Auto-approve, in the run request) lets tools run without asking when approvals are set to `ask` (never under `deny`); `PATCH /v1/chats/:id/run` `{ autoApprove }` changes it for the run in progress, from its next approval on (one already waiting still needs an answer). For a chat's first three messages (or while its title is still its first line), a tool-free `suggestChatTitle` call runs alongside the agent; its title is saved with `store.setAutoTitle` (never over a title the user chose) and sent as a second `chat` event before `done`.
- **Security**: listens on 127.0.0.1 only, rejects other `Host` headers (DNS rebinding) and non-JSON writes (cross-site form posts). Keep all three: the agent can write files.
- **Sign-in**: `features/auth/`. Off unless the root `.env` sets `SUPABASE_URL` and `SUPABASE_ANON_KEY` (`readAuthSettings` in `config/env.ts`: both or neither, https), and always off with `SIGN_IN=off` (the desktop app sets it; Electron drops empty env values, so emptying the two can't turn it off). Signing in is optional unless `SIGN_IN_REQUIRED=true` (`AuthConfig.isRequired`). `GET /v1/auth/config` (`AuthConfig` from `@app/shared`) is always open; `requireUser` runs before everything after it in `app.ts`: a request without an `Authorization` header is a guest's (`res.locals.user` null) when sign-in is optional and a 401 when it's required; a header sent is always checked: `Authorization: Bearer <Supabase access token>`, checked by `supabaseTokenVerifier` (supabase-js `getClaims`: the project's published keys locally, or its Auth server for shared-secret projects; only `role: authenticated`, so the legacy anon key is refused; a token that isn't JWT-shaped is a 401 without asking; Supabase unreachable is a 502, never a sign-out), cached per token until it expires. `AUTH_ALLOWED_EMAILS` (any case) narrows who gets in (403 otherwise). `GET /v1/auth/me` says who is signed in (null with sign-in off, or for a guest). The CSP's `connect-src` adds the Supabase URL so the built web app can sign in. The terminal socket is covered by its ticket, which needs a request `requireUser` let through. `/health` stays open. The CLI reads the files directly and doesn't go through this. Offline tests: `test/auth.test.ts`.
- **Logging**: pino (`src/logger.ts`) for HTTP. Agent runs log through `AgentLogger` from `@app/agent` (JSONL in `~/.nimbrio-ai/logs`, or `AGENT_LOG_DIR`). No `console.*`.
- **Env**: the root `.env`, loaded in `src/config/env.ts`: optional server values (port, CORS, HTTP log level, log folder, Supabase sign-in) via `loadAgentConfig`.
- **Agent settings**: `features/settings/` (`GET`/`PUT /v1/settings`), saved by `store.settings` in `~/.nimbrio-ai/agent-settings.json`. `AppSettings` keeps the saved settings in memory; runs take `settings.configFor(agentConfig)` once in `prepare`, so a save applies from the next message. The agent logger reads the level from it on every line.
- **Attachments**: `features/attachments/`. `POST /v1/workspaces/:id/attachments` takes one file as JSON (`{ name, type, data }`, base64), the only route with a larger body limit (`UPLOAD_BODY_LIMIT`, mounted before the 1 MB parser in `app.ts`). `GET …/attachments/:attachmentId/content` sends it: PNG/JPEG/GIF/WebP and PDF inline, everything else as an `application/octet-stream` download, so an uploaded HTML or SVG never runs as a page. `runs.service.ts` checks a run's `attachmentIds` exist before the stream starts.
- **MCP**: `features/mcp/`. Servers are app-wide (`/v1/mcp/servers`, `store.mcpServers`, `~/.nimbrio-ai/mcp-servers.json`); a workspace turns them on/off and approves its file at `/v1/workspaces/:id/mcp` (`store.mcp(workspace)`, its `.nimbrio-ai/mcp.json`); `GET`/`PUT …/mcp/enabled` reads or sets the whole on-list without starting anything (the workspace form), stopping the servers it turns off. `autoApprove` is per server, app-wide. Renaming keeps a server on where it was (`store.renameMcpServer`); app-wide edits wait until no chat runs. On start `store.importLegacyMcp()` moves old per-workspace server settings (approved files only) into the app's list.
- **Skills**: `features/skills/`. `GET`/`POST /v1/workspaces/:id/skills`, `GET`/`PUT`/`DELETE …/skills/:name` (`store.skills(workspace)`, one `.nimbrio-ai/skills/<name>.md` each; a different `name` in a `PUT` renames, a taken name is a 409). Names are kebab-case (`skillNameSchema`) and are the file name, so one can't point outside the folder; files are read without following links. A run's `skills` (names picked in the composer) are checked in `prepare` (`requireAll`) before the stream starts and passed to `runInChat`.
- **Prompt helpers**: `features/prompts/`, nothing saved. `POST /v1/prompts/improve` rewrites a message draft (`improvePrompt`); `POST /v1/prompts/instructions` writes a workspace's instructions (`writeInstructions` in `@app/agent`) from the user's request, the current text, the name and folder, plus `peekProject` (top-level names and the start of a README or manifest; plain files only, `O_NOFOLLOW`, nothing for the disk root or home). `POST /v1/prompts/skill` rewrites a skill's instructions as clear steps and suggests its description (`improveSkill`, a JSON reply). All use the default model unless `modelId` is given.
- **File edits by the user**: `PUT /v1/workspaces/:id/files/content` saves a file from the preview (`baseVersion` = the sha1 it opened; a different file on disk is a 409, no `baseVersion` overwrites); `POST /v1/workspaces/:id/files` makes an empty file or folder (parents too, 409 if it exists); `PATCH` renames or moves one (`{ from, to }`, 409 if `to` exists, never into itself); `DELETE ?path=` removes a file or a folder with its contents (204; the web app confirms first). Rename and delete act on the entry itself (`entryAt`: its folder resolved, the entry not followed), so a symlink is renamed or removed as a link and can't reach outside. Both use the agent's sandbox (`resolveInWorkspace`, `assertCanChange`): inside the workspace, never `.git`, `.nimbrio-ai` or the folder itself. They're the user's own actions, so no approval step. `GET …/files` also returns `emptyFolders` so new folders show, and `ignored`: what git ignores there (`git ls-files --others --ignored --exclude-standard --directory`, a wholly ignored folder as one `dir/` entry; empty outside a repository), for dimming.
- **File search**: `GET /v1/workspaces/:id/files/search?q=&mode=names|contents` (`files.service.ts`, using `findFilesByName` / `searchFileContents` from `@app/agent`): the agent's walk, so generated folders, symlinks and `.nimbrio-ai` stay out; plain text, any case, capped in results, files (1 MB, no binaries) and time.
- **Git diff**: `features/git/`. `GET /v1/workspaces/:id/git` lists what changed in the workspace folder since the last commit (`git status --porcelain -z` plus `--numstat`, staged and unstaged together, untracked included; an empty tree as base before the first commit). `GET …/git/diff?path=` diffs one file, and only a path that status listed, so it's never free-form. Read-only: git runs through `features/git/run-git.ts` (`runGit`, also used for the file list's ignored paths) without a shell, with fsmonitor, external diff and textconv off, no optional locks, no pager or prompt, and without this app's secrets.
- **Tasks**: `features/tasks/`. `AppContext.tasks` is the app's `BackgroundTasks` (from `@app/agent`, made in `index.ts`, passed to `runInChat` by `runs.service.ts`, stopped on shutdown and by `workspaces.service.ts` when a workspace is deleted or its folder changes). `GET /v1/workspaces/:id/tasks` lists the running ones (`BackgroundTask` in `@app/shared`), `GET …/tasks/:taskId` gives one with its output (`BackgroundTaskDetail`), `DELETE …/tasks/:taskId` stops it and everything it started (204). `POST …/tasks` `{ command, cwd? }` (`taskStartSchema`) starts one for the user from the Tasks tab (201, `chatId: null`): their own action like the terminal, so no approval, but still `refuseCommand`, a `cwd` inside the workspace (`resolveInWorkspace`), `commandEnv` and the 10-running cap (400).
- **Folder dialog**: `POST /v1/folders/pick` opens the operating system's own folder window on this machine (`features/folders/folder-dialog.ts`: AppleScript `choose folder` on macOS, PowerShell `FolderBrowserDialog` on Windows, `zenity` / `kdialog` on Linux) and waits for the choice; `isSupported: false` when there's none, and the web app falls back to its in-app browser (`GET /v1/folders`). User text reaches the dialog only as arguments or env, never inside a script. A failure other than Cancel (AppleScript -128) is an error, not a silent cancel; on macOS it retries without System Events, which needs the Automation permission. `GET /v1/folders/check?path=&workspaceId=` (`store.folderProblem`) says why a folder can't be used (another workspace uses it, or, when moving one, it already has `.nimbrio-ai` data) without creating anything; the workspace form shows it under the Folder field as it's typed or picked, and saving checks again.
- **Terminal**: `features/terminal/`. One shell per workspace in a PTY (`node-pty`, started in the workspace folder with the user's env minus this app's secrets, `withoutAppSecrets`), kept running across reconnects with recent output replayed. `POST /v1/workspaces/:id/terminal` issues a one-time ticket (30 s); the WebSocket `/v1/terminal/socket?ticket=` (handled from the server's `upgrade` event in `index.ts`) also checks Host and Origin, because browsers let any site open a WebSocket to localhost. `DELETE` stops the shell. `ensureSpawnHelper` fixes node-pty's prebuilt helper losing its executable bit.
- **Model providers**: `features/providers/`. Providers you sign in to with an account instead of an API key (today Cursor; the protocol code is `@app/agent`'s `cursor/`). `GET /v1/providers` lists who is signed in (`ProviderAccount` from `@app/shared`, never tokens); `store.providers` renews an expired access token whenever the sign-in is read (one renewal at a time; a 401/403 marks `needsSignIn`). Cursor's browser sign-in: `POST /v1/providers/cursor/logins` (201 `{ loginId, loginUrl, expiresAt }`; the verifier stays in this process's memory for 10 minutes, at most 10 waiting), `GET …/logins/:loginId` asks Cursor once (`pending`, or `connected` after saving the tokens; a Cursor failure is a 502 `UPSTREAM_ERROR` and the sign-in keeps waiting; unknown or expired is a 404), `DELETE …/logins/:loginId` cancels (204, idempotent), `DELETE /v1/providers/cursor` signs out (204, 404 when not signed in). `GET /v1/providers/cursor/models` lists the account's models from Cursor (`ProviderModel`; 400 when not signed in, 502 when Cursor fails); the web app adds one with `POST /v1/models` and `provider: 'cursor'`. Offline tests: `test/providers.test.ts`.
- **Models**: app-wide, stored by `@app/db` (`store.models`, `~/.nimbrio-ai/models.json`) and managed at `/v1/models` (`features/models/`). Each has an optional `contextWindow` (tokens, 2,000 to 20M; null uses the agent's 128K default) that `forRun` passes to the agent in `ModelSettings`. API keys go in but never come out: responses carry `hasApiKey`. A model's `provider` is `openai` (any OpenAI-compatible server) or `cursor` (no server or key: `store.models.settingsFor` gives it the Cursor sign-in's token, so it runs through `runs.service.ts`, the prompt helpers and the CLI like any other; an edit without `provider` keeps it). `runs.service.ts` resolves the run's model (`modelId`, or the default) and reasoning effort before the stream starts.
